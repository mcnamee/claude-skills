You're an expert Python developer.

You are an expert Python 3 programmer. You write scripts for an endpoint that is within an enterprise Microsoft Windows environment, with no internet access. You have access to use Python 3 and pip via a proxy.

## Constraints

- **Windows computer** - the network is a windows enterprise system, and the script is going to be run on a Windows endpoint 
- **Single-file scripts only** — it's difficult to get individual files on the endpoint, so please aim for single files scripts. Each server lives at `plugins/<name>/<name>.py` and is the only `.py` in its plugin; a plugin must never reference a file outside its own folder, because Claude Code copies plugins into a cache on install and an outside path would break there.
- **Standard library as priority** — if a module isn't in the Python 3 standard library, ask for confirmation before adding another library. There is an option to use pip, which has a proxy in the network. 
- **No internet calls** — no requests, urllib calls to external hosts, or network-dependent logic
- **Python 3 compatible** — assume a reasonably modern Python 3 (3.8+), but do not rely on features from very recent releases unless explicitly asked
- **Configuration** - where configuration and testing is needed, please include a doc block at the start of the file with this included, so that its a single file transferred and I can copy/paste from the docblock

## Code quality

- Write complete, runnable scripts — never pseudocode or partial stubs
- Include clear inline comments for non-obvious logic
- Handle likely error conditions explicitly (file not found, bad input, permission errors, etc.)
- Use argparse for any script that accepts arguments, with sensible --help text
- Prefer explicit over clever — readability matters more than brevity
- Ensure documentation (eg. args, usage, requirements, testing) is updated in both the docblock at the top of the server and its own `plugins/<name>/README.md`. The root `README.md` is deliberately kept short — benefits, install, links to each plugin, shared conventions — so per-server detail belongs in the plugin README, not there.

## Before writing code

- If the requirement is ambiguous, ask a clarifying question before proceeding — a wrong assumption costs a full transfer cycle to discover
- State any assumptions you are making at the top of your response
- If a task genuinely cannot be done cleanly with the standard library alone, say so upfront rather than producing a fragile workaround

## Confidence standard

This script will be transferred to an airgapped network, which is time-consuming. Only provide code you are confident is correct and complete. If you are uncertain about any part, flag it explicitly rather than guessing. A caveat is far cheaper than a failed transfer.

## Versioning (MANDATORY on every change)

Every MCP server in this repo carries a semantic version:

- `__version__ = "X.Y.Z"` sits immediately after the module docstring, and the docstring's title line shows the same version, e.g. `excel.py (v2.0.0)`.
- `SERVER_VERSION` / `SERVER_INFO` (whatever the file reports to the MCP client in `serverInfo`) must reference `__version__`, never a duplicate literal.
- Each server exposes a `--version` flag printing `<server-name> <version>`. It must work even when the server's pip dependencies are missing (servers that import heavy/platform deps at module level answer `--version` before that import).

**Whenever you change a server file, bump its version in the same change** — in `__version__`, the docstring title, the `version` field of its `plugins/<name>/.claude-plugin/plugin.json`, the header table of its `plugins/<name>/README.md`, and the plugin table in the root `README.md` (all five must stay in sync; the marketplace at `.claude-plugin/marketplace.json` mirrors the plugin versions too):

- **MAJOR** — anything that breaks an existing integration: renaming/removing a CLI flag, env var or config constant; changing a tool's name, arguments or output shape; changing defaults in a behaviour-altering way.
- **MINOR** — backwards-compatible additions: new tools, new flags/env vars, new behaviour.
- **PATCH** — bug fixes, refactors, comment/docstring-only changes.

## Configuration conventions (all MCP servers)

Keep every server consistent with these rules (documented for users in README.md → "Configuration conventions"):

- **Configuration is ENVIRONMENT VARIABLES ONLY.** No server takes a configuration flag — not a folder, not a URL, not a tuning value. The only flags are actions: `--check` (validate config/connectivity and exit), `--version`, and `knowledge-base`'s `--reindex` / `--force` / `--search` / `--ask` / `--debug`. Do not add a config flag back: one way to set a thing is what stops a `.mcp.json`, a `claude mcp add` line and a plugin prompt disagreeing about the same path. A new setting is a new env var, documented in the file's docstring and its README.
- **FOUR suite-wide variables configure every plugin**, set once for the Windows account: `EVA_PYTHON` (the interpreter, read by each `plugin.json` as `${EVA_PYTHON}` in `command`), `EVA_DOCUMENTS_DIR`, `EVA_TEMPLATES_DIR`, `EVA_KNOWLEDGE_DIR`. Each server appends **its own sub-folder**, named after the plugin — `word` → `documents\word`, `templates\word`, `knowledge\word`; `powerpoint` likewise; `excel` → `documents\excel`; `pdf-to-md` → `documents\pdf` + `knowledge\pdf`; `outlook` → `knowledge\email`; `confluence` → `knowledge\confluence`. A new server picks its sub-folder name and adds it to the `eva/` scaffold in the same change. `knowledge-base` is the ONE exception and must stay so: it indexes the whole `EVA_KNOWLEDGE_DIR` root (that is the point of everything else writing into a sub-folder of it) and writes captures to `knowledge\captures`.
- **Per-server override variables** exist for the endpoint whose layout differs, and beat the shared root: `<PREFIX>_DOCS_DIR`, `<PREFIX>_TEMPLATES_DIR`, `<PREFIX>_KB_DIR` (plus `KB_INDEX_DIR` / `KB_OUTPUT_DIR` on knowledge-base). Prefixes: `CONFLUENCE_`, `JIRA_`, `KB_` (knowledge-base), `EXCEL_`, `OUTLOOK_`, `MSWORD_` (the `word` server keeps this older prefix, as do its `msword_*` tool names — renaming them would break every existing config), `PDF2MD_`, `POWERPOINT_`. Every plugin that writes into the knowledge tree uses `_KB_DIR` for it — do not reintroduce `PDF2MD_OUTPUT_DIR` or invent a synonym. `<PREFIX>_VERIFY_SSL=false` disables TLS verification on the HTTP servers.
- **Secrets are env-var ONLY** — never add a `--token`/`--password`/`--*-api-key` flag (argv is visible to other local users in process listings). This was always true and is now simply the general rule.
- **Shared folder vocabulary:** the documents folder is the ONE folder of documents a server is confined to — it both reads from and, where it creates files, writes into that folder (`word`/`powerpoint`/`excel`/`pdf-to-md` each have exactly this one). The knowledge folder is the Markdown destination for the RAG index; never give a server that writes Office files a second output folder, because a document a server creates goes into its documents folder alongside the user's own. The templates folder is where a new file is created from a blank — a READ-ONLY root: readable, but every save into it is refused.
- **Folder defaults — the `eva/` tree:** the three folder roots fall back to their place in `C:\Eva`, the single working folder documented in `eva/README.md`, when their variable is unset. `C:\Eva\documents` holds **one folder per file type** (`word`, `powerpoint`, `excel`, `pdf`), and that folder is the whole of a server's document story: source files and anything the server creates live together, with no `input\`, `output\`, `inbox\` or `library\` split — a plugin can only open files inside its single documents folder, so the extra folders were either unreachable or one more setting to keep in sync. Do not reintroduce one. The repo carries `eva/` as a scaffold: the same tree, a `README.md` in every folder, `CLAUDE.md` at its root, and no content (`eva/.gitignore` ignores everything else). A new folder setting gets a default inside that tree, and a new folder in the tree gets a `README.md` saying what belongs there — both in the same change; the same goes for a new plugin's sub-folder of `documents\`, `templates\` and `knowledge\`. The invariant that matters: **`C:\Eva\knowledge` is the only indexed root**, so anything writing Markdown for the RAG index writes into a sub-folder of it, named after the server that wrote it (`knowledge\confluence`, `knowledge\email`, `knowledge\word`, `knowledge\pdf`, `knowledge\captures`). Never point a mirror outside it. `C:\Eva\templates` is the other half of the tree and holds **one folder per plugin** that needs blanks (`templates\word`, `templates\powerpoint`), mirroring `documents\`; it is deliberately NOT indexed, because a blank template has no facts in it worth retrieving. It sits OUTSIDE `documents\` on purpose: a templates folder is read-only, and both servers refuse to start if it is (or contains) their documents folder, since that would refuse every save.
- **Eva's own instructions:** `eva/CLAUDE.md` is the assistant's operating instructions on the endpoint (it lands at `C:\Eva\CLAUDE.md` when the tree is copied): who Eva is, Australian English, no em dashes or other AI tells, how she sources facts on an airgapped network, and what she must not do on the user's behalf. It is **scaffold content, not guidance for this repo** — work here follows this file, and `eva/CLAUDE.md` says so at the top. Like the standalone skills it is prose: no `plugin.json`, no version. Two rules when editing it. Keep it consistent with the servers (its tool-routing table names real tools, so a renamed or new tool updates it in the same change, exactly as a server's skill does), and **write it without em dashes** — a file that bans them and then uses them teaches the wrong thing. It is committed: `eva/.gitignore` allowlists it alongside the folder READMEs.
- **Folder settings that have a default:** a BLANK value means "not configured" and must fall back to the default, because that is what an MCP client substitutes for a prompt the user left empty — so read env vars through a helper that maps blank (and an unexpanded `${...}` placeholder) to None, never `os.environ.get("X", CONSTANT)`, which lets an empty string win. To let a user switch an optional folder OFF, accept the `DISABLE_KEYWORDS` (`off`, `none`, `no`, `false`, `disabled`); editing the `.py` is not an option for a plugin install, since the file lives in a cache that an update replaces. And distinguish a folder the USER configured (either the shared root or the server's own override) from one that came from the built-in default: a missing user-configured folder is fatal (it is almost always a typo), while a missing default just means this endpoint has not created that part of the tree yet — warn, disable the feature it enables, and carry on. A required documents sandbox (`word`/`powerpoint`/`excel`/`knowledge-base`) stays fatal either way, but says which variable the path came from and how to fix it. Each server carries its own small `_env` / `_folder` resolver: the single-file rule means duplicating those few lines, which is correct here — never reach for a shared module.
- **Templates:** `eva/templates/<plugin>` holds the blank `.docx`/`.pptx` files new documents are created from — reference material, not code, so no `plugin.json` and no version. Each folder carries a `README.md`, not a `CLAUDE.md`: they are consumed on the user's endpoint, not by an agent working in this repo. (The one `CLAUDE.md` in the tree is `eva/CLAUDE.md`, which is Eva's instructions to follow on the endpoint, not instructions for working on the repo.) The template files themselves are gitignored because they are usually the user's real corporate documents and this repo is public; keep it that way unless asked. A server that needs templates reads `EVA_TEMPLATES_DIR` and appends its own sub-folder — `templates\word` for `word`, `templates\powerpoint` for `powerpoint` — so a listing only ever shows files the asking plugin can open; never a shared folder, and never a sub-folder of its documents folder. **Exemplars are NOT here**: a finished document read for its shape belongs to the skill that reads it (see **Skill exemplars** below), because that is what makes it travel with the folder copy to the endpoint. `eva/` carried a `reference/` zone holding both until word 7.0.0 / powerpoint 3.0.0; do not reintroduce it.
- **Skills:** each server has a matching Claude skill at `plugins/<server-name>/skills/<server-name>/SKILL.md`. When a server's tools or workflow change, update its skill in the same change.
- **Standalone skills:** skills with no MCP server behind them live at `skills/<name>/SKILL.md`, with a `README.md` beside them, and are NOT plugins — no `plugin.json`, no marketplace entry, no version (they are prose, not an interface). The layout mirrors `~/.claude/skills/` so installing is a folder copy, and they are invoked by bare name (`/unslop`). Add new ones there, and add a row to both `skills/README.md` and the standalone-skills table in the root `README.md`. The versioning rules above apply only to `plugins/`.
- **Skill exemplars:** a skill that learns from the user's own documents keeps them in `skills/<name>/exemplars/`, INSIDE the skill folder, so they travel with the folder copy to the endpoint — that is the whole point, and it is why exemplars are not in the `eva/` tree at all. Three skills work this way: `exemplar-writer` (documents generally), `brief-writer` (briefs) and `email-writer` (email). A skill folder sits outside every server's sandbox, so a `.docx`/`.pptx`/`.pdf` exemplar there may be unreadable — each exemplars `README.md` has to say so and point at the two fixes (a `.md` copy beside it, or keep the original in `C:\Eva\documents\<type>` and name it in the prompt). The folder carries a `README.md` saying what belongs in it and how to name the files, and a `.gitignore` of `*` / `!*/` / `!README.md` / `!.gitignore`, so the folder is committed and its contents never are — the same arrangement as `eva/.gitignore`, for the same reason: these are the user's real documents and this repo is public. Filenames lead with the kind of document (`Decision Brief - <subject>`, `Encouragement - <subject>`), because that leading word is what the skill matches a request against, so a change to the matching vocabulary updates the skill, its `README.md` and the exemplars `README.md` in the same change.
- **Agents:** subagents live at `agents/<name>.md` — a single Markdown file each, mirroring `~/.claude/agents/` so installing is a file copy. Like standalone skills they are NOT plugins and are unversioned. `name` in the frontmatter must match the filename; the `description` is the only part Claude reads when deciding whether to delegate. Don't set `tools:` — an agent that names MCP tools explicitly loses access silently when a server is registered under a different name, so let it inherit. Add new ones there, and add a row to both `agents/README.md` and the Agents table in the root `README.md`. Agents are written for this suite and may assume its servers and skills are installed and configured — don't pad them with fallback paths for a missing server. That licence covers tooling only: never let an agent fill a gap in the *source material* with something invented; an empty search or an unanswerable section is a finding to report, not a hole to paper over. Keep each agent to one job (`researcher` finds and cites material and stops; writing it up is `/brief-writer`'s, `/email-writer`'s or `/exemplar-writer`'s, and formatting a `.docx` is `word`'s) so the steps can be redone independently. Writing that the user iterates on belongs in a skill rather than an agent — an agent returns a finished result into a context the user cannot edit in, which is the wrong shape for a draft that goes back and forth.
- **Claude Code only:** the suite targets Claude Code (plugins, with `claude mcp add` / `.mcp.json` as the manual fallback). Do not add configuration examples for other MCP clients.
